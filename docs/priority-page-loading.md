## Implementation contract

- The root layout continues to await locale cookies only, never the database. A global `loading.tsx` supplies bilingual accessible pending feedback; the dashboard returns its static heading immediately with a Suspense data boundary. Data replaces the fallback after the actual response. Dashboard reads use the existing server-only/no-store helper with a 15-second bound; failure shows no fabricated metrics, does not unlock background requests, and offers an explicit native reload.
- One client-local admission queue permits only **`/changes` and `/issues`**, one short eligibility window each per mounted root layout, after successful dashboard data hydration and an idle delay. Each window expires after two seconds; navigation/hiding/cleanup revoke it sooner. This bounds route admissions and eligibility time, not an exact count of Next internal HTTP attempts. Explicit full `Link prefetch=true` is used for those sidebar links, because automatic dynamic-route prefetch with loading boundaries can fetch only the shell. Other shell/dashboard links use `prefetch=false`; detail, private controls, arbitrary queries and expensive release aggregation are not added to the background set. This is a deliberately finite representative prefetch budget, not all-page warming.
- Explicit navigation never waits for this queue. Normal same-origin navigation clicks, browser history, leaving the dashboard and hiding the document revoke unsent work; generation guards reject stale idle callbacks. Already sent Next RSC/API/database work is **not** preempted or claimed to be cancelled. Foreground network bandwidth is not guaranteed by a JavaScript queue. Native Next routing keeps old route responses from replacing the current route; tests exercise delayed dashboard completion after navigation.
- Direct entry to another page loads that page rather than fetching dashboard first. No generic proxy, shared server payload cache, session data cache, new endpoint, dependency, schema, identity, permission or deployment setting is introduced. The existing `server-only`, `no-store`, current permission filtering and disabled write gates remain.
- The shell paints a full-height dark left rail. The sticky sidebar has a viewport-height independent scroll area, including the final links/footer; the main surface remains light. Existing narrow-screen hidden-sidebar layout is preserved.

## Evidence and acceptance

Tests are added before feature implementation for the queue, real React response streaming and failure presentation. The original implementation fails the queue/missing-loading checks and cannot emit the dashboard shell while the test response remains held. Unit tests cover generation cancellation, finite budget, successful progressive data, failure/native retry, and no backend reads in loading markup. A separate loopback fixture with explicit deferred responses rejects unexpected paths, query parameters, mutations and credentials.

Four additive actual-browser cases cover held-dashboard shell visibility before release, exactly two bounded full-data prefetches afterwards, long-page/short-viewport sidebar and mobile layout, navigation while dashboard is held with no stale UI replacement, failure/redaction/native retry, and navigation immediately after the first background admission with the remaining queue revoked. Their strict same-origin GET/HEAD/path allowlist uses `route.continue`, not response buffering, through a fixed-upstream loopback streaming test proxy that rejects all 3xx before forwarding and never follows redirects; the previous B1 cases retain their existing buffered isolation and assumptions. Report acceptance requires all **six exact title/file pairs**, actual Chromium runtime annotations, zero skips/failures/flaky/retries. No workflow, runner, dependency, sandbox or permission policy is changed. Browser discovery and SSR/unit tests are not browser execution; actual execution is only on the already approved macOS CI runner.

Public performance baseline attempt: one unauthenticated frontend GET could not establish a connection within 10.003 seconds (HTTP000, zero downloaded bytes; TCP/TLS/TTFB unavailable). This is an execution-environment connectivity limitation, **not** a measured website response or database delay. No alternate route/retry bypassed earlier browser access refusal. No claim is made that the live website or database is faster, or that the user's region has been measured. Successful synthetic streaming establishes ordering, not production latency.
