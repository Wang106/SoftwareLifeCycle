# Private bounded distribution selectors (P3)

## Approved minimal read policy

This package adds private preparation help for exactly three existing command forms,
not a global object catalogue or a new write policy. A current ACTIVE USER and valid
claimed browser session must have an ACTIVE membership in the exact application
release project: DISTRIBUTION_AUTHORITY for delivery/package preparation and
PRODUCTION_AUTHORITY for authorization scope. PLATFORM_ADMIN alone is not an
exception. Anonymous/non-OIDC fallback and aggregate grant counts grant no access.
Missing and foreign targets return the same unavailable result, without foreign counts.

The independent frontend PRIVATE_DISTRIBUTION_SELECTION_MODE and exact approved API
base/app origin default off. The existing offline readonly inventory requires it off.
No actual identity, role, secret, security/provider setting, CI or company deployment
is changed. Existing business write authorization remains independently authoritative.

## Three exact targets, minimal fields

- An explicitly supplied application release plus explicit recipient type/code/purpose
  resolves its effective RELEASE decision and approved frozen snapshot. Only eligible
  snapshot artifact UUIDs and presentation/hash/policy fields are returned. INTERNAL_ONLY
  files are never selectable; existing recipient-specific frozen rules take precedence
  over generic rules, including DENY overrides. No storage_reference, binary contents,
  credentials, unrelated rules or foreign object totals are exposed.
- An explicitly supplied delivery-package UUID identifies one exact revision and its
  fixed recipient/purpose. Existing READY/APPROVED eligibility, nonempty package and
  active chain are respected. This does not introduce a latest release-decision or
  approval requirement that the existing distribution-creation command does not have.
- An explicitly supplied distribution UUID supplies exact release/customer/project/
  purpose context and bounded ACTIVE site/line choices within that customer/project.
  It follows existing authorization-creation latest RELEASE snapshot and distribution
  status/recipient semantics, without adding a package READY restriction. Finite versus
  unlimited batch scope and restriction text remain explicit user choices.

Private GETs use bounded transactions/current authority checks and release locks on
completion; they never create business or audit records. Paging filters eligibility
before the bounded limit and uses stable identifiers; subsequent pages pin source
snapshot/decision identity rather than mixing candidates from changed contexts.

## Existing form integration

The user explicitly loads candidates and explicitly applies a selection. No automatic
query, recipient guess, submission or approval occurs. Public sample profiles are never
used as real-data authority. Applied package recipient and authorization scope come
from exact private context, not similarly named records. Original identifiers, file
names and scope text remain raw; labels/instructions are bilingual.

Changing target or relevant recipient/purpose invalidates unattempted selection and
confirmation. Stale asynchronous responses cannot apply to a different form/target.
Once an attempt exists, especially an unknown result, its original request remains
frozen and selection cannot rewrite it. Existing manual legitimate preparation stays
available as a deliberate fallback; switching away from private selection clears its
context rather than retaining an apparent verification badge.

Active site/line status is observed by this selector only. Existing authorization
creation stores the chosen site/line codes and does not itself resolve or recheck
active manufacturing rows; deployment creation performs that active-line check. This
package does not expand the authorization writer or promise that a selected line
remains active between reading and creating a DRAFT authorization.

A selector result is a bounded observation, not a capability or durable eligibility
promise. Existing write bodies and server revalidation remain unchanged. In particular,
old delivery creation does not gain a new caller-supplied decision pin: changed source
conditions can cause rejection and require deliberate fresh preparation. Unknown
attempts must be resolved using their original audit, never replaced with a new key.

## Acceptance boundaries

Required tests cover auth/session/project role/admin-only denials, target binding,
policy precedence and omitted fields, exact revision/recipient, active site-line scope,
pagination/source drift, no writes, raw bilingual rendering, stale callbacks and frozen
unknown attempts. Real PostgreSQL coverage and complete exact-head CI remain mandatory;
synthetic component/proxy tests are not real browser/provider/multi-user acceptance.

Final exact commit/tree/PR, independent review, CI artifacts and fresh main/provider
results are recorded in closure evidence. Overall milestone acceptance stays36/44=82%
until its actual criteria pass; adding selectors does not complete external identity,
operations, company-deployment, VIN, real-AI or binary-storage requirements.
